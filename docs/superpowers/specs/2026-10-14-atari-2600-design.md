# The Atari 2600: design

Written 14 October 2026. This is the design for the next machine on the core, after the Electron. It follows [the machines programme](2026-09-30-machines-and-site-design.md), where "implemented" is defined, and [the core's design](2026-09-29-6502-design.md). The [NES design](2026-10-05-nes-design.md) is the pattern for a console with no system ROM, a cartridge flow and two regions in one row, and [the NES's lazy chips](2026-10-06-nes-lazy-chips-design.md) are the pattern for its speed pass. The case for building it next is in [the research memo of 13 October](../../research/NextMachines_20261013/NextMachines_20261013.md), Finding 1.

## What is being built

The Atari 2600 (1977, sold first as the Atari Video Computer System): a MOS 6507 (an NMOS 6502 in a 28-pin package, with 13 address lines and no interrupt pins), the TIA (Television Interface Adaptor: the picture, the sound, the fire buttons and the paddle inputs), a 6532 RIOT (128 bytes of RAM, two I/O ports and an interval timer), a cartridge slot, two joystick ports and six console switches. It has no system ROM and no frame buffer: the program draws each line as the beam crosses the screen. It runs in the browser at 6502.dbhq.uk. **NTSC and PAL are both built**, as one registry row, one library and one page, with a region switch.

**It counts as implemented when all of these hold.** In both regions, the headless machine passes its chip tests and every trusted test of the pinned `missingno-vcs-tests` suite (the trust split is under "Proof"), and every recorded test gives its recorded outcome. The bundled homebrew boots to its recorded frame, compared to the pixel. The machine runs in the browser with picture, sound, two joysticks and the console switches, and the real-browser check passes. All of it runs in CI. The registry row `atari-2600` then becomes `running`, and the home page count goes up by one, computed from the registry as before.

## Parts

Two new libraries beside the NES's, `Dbhq.Machines.Atari2600` and `Dbhq.Machines.Atari2600.Wasm`, and a test project `tests/Dbhq.Machines.Atari2600.Tests/`. The machine uses the existing `Nmos6502` variant, so the core needs no change. Each part is one file with one job, tested alone.

| Part | What it does |
|---|---|
| `Atari2600Bus` | The CPU's bus. Keeps the low 13 address lines and drops the rest (the 6507 has no A13 to A15). Decodes the TIA, the RIOT's RAM and its I/O, and the cartridge, with every mirror. Each `Read` and `Write` advances the TIA by three colour clocks and the RIOT by one cycle, and the cartridge sees the access. Holds the WSYNC halt, and the last byte on the data bus for the bits the TIA does not drive |
| `Region` | NTSC or PAL: the colour clock, the CPU clock, the palette and the picture window. One place holds every number that differs, so no chip tests for a region by name |
| `Tia` | One method, `Tick()`, steps one colour clock. Owns the horizontal counter, the playfield, the two players, two missiles and the ball, their position counters and motion clocks, HMOVE, the collision latches, the input latches and the two sound channels. Writes a line of colour numbers into the frame, and starts a new frame at VSYNC |
| `Riot6532` | 128 bytes of RAM, ports A and B with their direction registers, the interval timer and the PA7 edge detect |
| `Cartridge` | Reads a file, chooses the board by size, refuses anything else with a plain message |
| `IBoard` and `Boards/` | One class each: `Plain` (2K and 4K), `F8`, `F6`, `F4`, `Fa`. A board sees every access, read or write, because the cartridge slot has no read/write line |
| `Controllers` | The two joysticks on port A, the fire buttons on the TIA's inputs, and the console switches on port B |
| `FrameBuffer`, `SampleBuffer` | The frame as colour numbers and as RGB for the region, and the sound as samples at the host's rate |
| `Atari2600` | Joins the parts for a region, powers on, resets, runs a frame, and exposes the frame, the samples, the joysticks and the switches |

### The 6507 on the core

The 6507 is an NMOS 6502 with fewer pins, and runs as `Nmos6502` (`docs/the-6502-family.md`). The 13-bit address is the bus's business, not the core's (rule 2): the core puts out a 16-bit address and the bus ignores the top three bits, so the reset vector at `$FFFC` is read from `$1FFC`. The 6507 has no IRQ or NMI pin, so the bus never raises either line. Its RDY pin is used, for WSYNC.

### The bus, the halt and the order inside a cycle

**WSYNC.** A write to WSYNC pulls the CPU's RDY line low until the TIA reaches the start of the next line. An NMOS 6502 stops only on a read cycle when RDY is low: a write goes ahead, and a read is repeated, with the address held, until RDY is released. The bus models this as the NES's DMA halt is modelled: the next `Read` call after the WSYNC write runs repeated reads of the same address, each a full cycle that advances the TIA and the RIOT, until the line starts, then makes the read and returns. Every one of those cycles is a bus access (rule 1). A read-modify-write of WSYNC writes twice before it stops, which the suite's `cpu/rmw-wsync` test checks.

**The floating bus.** A TIA read drives only data bits 7 and 6. The rest are what was last on the data bus. The bus keeps that byte, and the suite's `cpu/floating-bus`, `cpu/open-bus` and `cpu/partial-drive` tests check it.

**The order inside a cycle.** Which of the cycle's three colour clocks run before the access, and which after, decides when a TIA write takes effect on the line. The plan fixes it from the fact sheets and the suite's `tia-timing` tests, and records the choice and what it was chosen over, as the NES plan did for its dots.

**Mirrors.** The TIA answers wherever A12 and A7 are low, so it also appears at `$0100` to `$017F`, where the stack can reach it. The RIOT's RAM appears at `$0180` to `$01FF` as the stack. The suite's `cpu/stack-aliases-*`, `riot/ram-mirrors` and `riot/io-mirrors` tests check the decode, and its README warns that a wrong decode scrambles every test's first frames.

### The RIOT, against the KIM-1's 6530

`src/Dbhq.Machines.Kim1/Rriot6530.cs` is the nearest existing code. It is read as a guide and its tests' shape is copied. The differences, to be confirmed against the 6532 data sheet in the fact sheet before any code:

| | 6530 (KIM-1) | 6532 (Atari 2600) |
|---|---|---|
| Memory | 1 KB mask ROM and 64 bytes of RAM | No ROM, 128 bytes of RAM |
| Selecting RAM or I/O | Fixed by the mask-programmed chip selects | The RS pin, which the 2600 wires to A9 |
| Interrupt output | Shared with PB7 | A pin of its own, not connected on the 2600 |
| PA7 edge detect | None | A flag set on a rising or falling edge of PA7, with its polarity and enable chosen by a write |
| Reading the flags | Timer flag only | A flag register: bit 7 the timer, bit 6 the PA7 edge; reading it clears the edge flag |
| Timer | Divide by 1, 8, 64 or 1024; after zero it counts down once a cycle | The same, with the read on the cycle the timer passes zero to be checked against the suite's `riot/timer-underflow-read` |

On the 2600, port A reads the two joysticks and port B the console switches. The RIOT is clocked once a CPU cycle.

### The TIA

The TIA has no frame and no vertical counter. A line is 228 colour clocks, 68 of horizontal blank and 160 drawn, and a CPU cycle is three colour clocks. The program starts a frame with VSYNC and blanks lines with VBLANK. Each object has a position counter clocked by the colour clock while the line is drawn. A RESP write restarts it, and HMOVE adds extra clocks during the blank, which also stretches the blank by eight clocks (the "comb"). An HMOVE written late in the line, or a motion register written while HMOVE's clocks are still running, gives the effects games use on purpose. **The model is built from the TIA's own logic, its counters and latches, so that these effects come from the same mechanism as on the chip, and not from a list of special cases.** The sources are the TIA's schematics and the documents in "Where the code comes from".

**Collisions.** Fifteen latches, one per pair of objects, set as pixels overlap and cleared by CXCLR.

**Inputs.** INPT4 and INPT5 are the fire buttons, with the latch that VBLANK bit 6 turns on. INPT0 to INPT3 are the paddle inputs: not modelled, they read as a paddle at rest would, which the fact sheet states.

### Cartridges and bank switching

A cartridge appears at `$1000` to `$1FFF`. A 2K image appears twice. The bank-switched boards watch for an access to a hotspot near the top of the window, read or write alike, and the new bank is visible from the next cycle. The CPU's dummy reads count, which is why every bus access has to be the CPU's real one.

| Board | Size | What switches it |
|---|---|---|
| Plain | 2K, 4K | Nothing |
| F8 | 8K | `$1FF8` and `$1FF9` |
| F6 | 16K | `$1FF6` to `$1FF9` |
| F4 | 32K | `$1FF4` to `$1FFB` |
| FA (CBS RAM Plus) | 12K, and 256 bytes of RAM | `$1FF8` to `$1FFA`, and, by the suite's account, only when data bit D0 is 1. The RAM is written at `$1000` to `$10FF` and read at `$1100` to `$11FF`, because the slot has no read/write line |

The hotspots and FA's RAM ports agree with the suite's headers for `bank-f8`, `bank-f6`, `bank-f4` and `bank-fa`, read on 14 October 2026, and the fact sheet gives a second source for each. Which bank a board powers on in is undefined on the hardware (the suite's `cartridge/power-on-bank` test says so). The model picks one, and `docs/known-differences.md` records the choice.

A file of any other size is refused with a plain message naming the size and the boards that are modelled. A file of a modelled size made for an unmodelled board (an 8K E0 game, say) runs as the board of that size and fails. The page says so, and the issue to detect the board from the image covers it.

### Input

Two joysticks, each four directions and a button, and the console switches: Reset and Select, which spring back, and the left and right difficulty switches and the colour or black and white switch, which stay where they are put. The machine takes any combination, as the NES's takes any pad mask, including directions a real joystick cannot press together.

### Picture and region

The frame is 160 colour numbers wide and as many lines as the program makes between two VSYNCs, up to a limit, so a program that never strobes VSYNC still ends a frame. The page shows a fixed window of lines per region, as a television would. A short or long frame shows as it is, not stretched. The window and the pixel shape come from the fact sheet. The page says it models the picture and is not a CRT.

**Region.** A switch chooses NTSC or PAL. A 2600 image has no header, so the switch starts at NTSC, the page shows how many lines a frame has, and it suggests PAL when the frames are PAL's length. It does not change the region by itself. The switch changes the palette and the clock at once.

### Sound

Two channels, each with a 4-bit control register choosing the waveform from the TIA's polynomial counters, a 5-bit frequency divider and a 4-bit volume, clocked twice a line. The mixed output is resampled in the machine to the host's rate and played by an `AudioWorklet`, as the NES's is. Sound is off until the visitor clicks. CI checks the samples, not the audio.

## Where the code comes from

**No code is taken from another emulator.** Stella and Gopher2600 are GPL and this repository is MIT, and missingno is left out for the reason above. The chips are written from documents, in fact sheets under `docs/atari-2600/facts/`, each written before its code and naming the source of every statement, as the NES's sheets do: the Stella Programmer's Guide (Steve Wright, Atari, 1979), the TIA's schematics, Andrew Towers's TIA hardware notes, and the 6532 data sheet. The suite's test headers, which state each behaviour and how a wrong model shows, are read as a source too. They are the behaviour to match, and no code is taken from them.

## Proof

Five layers, built in this order. All run in CI.

1. **Chip tests, one file per part, each alone.** The RIOT (RAM, ports and directions, the timer at each divider and past zero, the edge detect, the flag register). The TIA (the horizontal counter, WSYNC, RSYNC, VSYNC and VBLANK, the playfield, each object, HMOVE, the collision latches, the input latches, each sound channel's waveform). Each board's banking and the refusals. The bus's decode, mirrors, the floating bus and the halt. Each test that touches the palette or the clock runs for both regions.
2. **The suite, through the real bus.** The fork's ROMs run headless until the byte at `$80` is `$A5` or `$5A`, within a limit, and on a fail the test reports `$81` to `$83` (which check failed, what was seen, what was expected). The `_ntsc` build runs in NTSC and the `_pal` build in PAL. The SECAM builds are not run.
3. **The suite's reference pictures.** A screenshot test renders a frame and compares it with the test's `_ntsc.png` or `_pal.png`. The comparison is as a partition: every colour in the reference must map to exactly one TIA colour number in ours, and the reverse, at every pixel. So it is exact about which pixel is which colour and does not depend on missingno's palette. The palette is checked by the chip tests.
4. **Boot check of the bundled game.** The headless machine runs a set number of frames in each region, and the frame's SHA-256 is compared with `machines/atari-2600/expected-frames.json`, written by a recorder and never by hand. The recording is looked at by eye first, and its command is in the journal. The browser check reads the same file and compares the canvas to the pixel, as the NES's does.
5. **Real-browser check.** `browser-check.mjs` grows to load the page in headless Chrome, press Start, wait for the game's first frame and compare it, move a joystick and press Reset through the page and check the picture changes, load a test ROM through the picker, flip the region and check the colours change, and check for no console errors and the headroom line.

### Which suite results are trusted

At the pinned commit the suite has 127 tests, of which 27 have reference pictures (counted on 14 October 2026 in a clone at `891c079` with `ls roms/*/*.asm | wc -l` and `ls roms/*/*_ntsc.png | wc -l`). The README says it was "Verified on real hardware (an Australian PAL all-black unit, July 2026)", that the cartridge tests could not be run on that console, and that contested cartridge behaviour is marked "untested on hardware" in the test's header.

| Results | Status | Why |
|---|---|---|
| Self-tests in `cpu/`, `riot/`, `collision/`, `tia-timing/`, `tia-render/` and `harness/sanity`, both regions | **Trusted**: in the acceptance test, must pass | Checked on a console, and the README says their verdicts do not depend on the region |
| Self-tests in `cartridge/` for the modelled boards (`mirror-2k`, `bank-f8`, `bank-f6`, `bank-f4`) | **Trusted** | The behaviour is plain and documented elsewhere, and the headers do not dispute it |
| `cartridge/bank-fa` and `cartridge/bank-hotspot-window` | **Recorded** | Their headers say "untested on hardware". FA's header says the board "switches banks only when data-bus bit D0 is 1", and that this gate is the untested part |
| `cartridge/power-on-bank` | **Recorded** | Its header says it "is a diagnostic, not a pass/fail test": it reports which bank the board woke in |
| Screenshot tests (`tia-timing/`, `tia-render/`, `harness/calibration`), both regions | **Recorded** | The references are missingno's renders, aligned to one PAL console's captures. NTSC was never captured. They are the main check of late HMOVE and the object quirks, so a failure is triaged as a likely bug first |
| Cartridge tests for unmodelled boards, and every SECAM build | **Not run** | The boards are issues; SECAM is not modelled |

**Recorded** means the test runs in CI and its outcome (pass, or the fail code and values, or the count of mismatched pixels) is written by a recorder to `machines/atari-2600/suite-outcomes.json`. CI fails when an outcome changes, so a change is seen and goes in the journal before the file is recorded again. A trusted test that fails is fixed, or it moves to recorded with a `docs/known-differences.md` entry giving its cause and Dan's agreement. Nothing is skipped silently. The suite is checked on one console, and TIA behaviour is known to vary between chips and console models, so a trusted result is the behaviour of that console, which the page says.

**A mutation pass follows**, as on every machine: break one thing at a time and confirm a test fails. Anything that survives gets a test or an entry in `docs/known-differences.md`.

## Speed

The TIA does three colour clocks of work for every CPU cycle, the same pattern as the NES's PPU, which needed the lazy chips work after it went live. So the plan has a **speed milestone** (task 8): a headless machine with the bus, the RIOT and the TIA's picture, measured in headless Chrome, AOT and interpreter, in both regions, with the NES plan's rule for what happens next. The figure is recorded with its command.

**The speed pass is planned now and built after the machine counts**, as its own design and plan and its own pull request, on Dan's order, as the NES's was. Rule 1 allows a chip to be advanced lazily only when a differential over real programs shows the same state at every point where it can be seen. The 2600 is a good case for it. The TIA can be seen only at the CPU's TIA accesses, at the end of the WSYNC halt (which is computed from the horizontal counter) and at the frame's end. The RIOT's timer can be worked out when it is read. The expected shape, from the NES's six tasks: the gate (the differential, with synthetic cartridges that sweep register writes across the line), the lazy TIA, a renderer for runs of colour clocks with no write and no motion pending, the RIOT timer worked out on read, the sound in batches, and the measurement. The hooks it needs are built in task 4.

## The browser host

**What it gets for free.** The shared `site/public/machine-host.js` loads the WebAssembly on Start, runs the frame loop against a cycle budget, pauses when the tab is hidden and shows the headroom line. The NES's panel already has the rest of a cartridge console: the file picker and drop target with its size limit and plain refusal, the region control and the sentence that says why it is set, the Gamepad API mapping, the touch pad, the `AudioWorklet` ring with its drop rule, the picture's pixel shape, and the browser check's comparison with an expected frame.

**What moves.** Under the rule that shared parts are extracted when a second machine needs them, the picker, the region sentence, the gamepad poll and the sound worklet move out of `nes.js` and `nes-audio.js` into shared modules. The NES's own browser check must pass unchanged.

**What is new.** The console switches on the panel, shown in the positions they are in, with keys for each. Two joysticks on the keyboard and two gamepads. The 160-wide picture in the region's window and pixel shape. The line count and the PAL suggestion. The panel says which board a file was run as.

## The 3D models

**A later, separate task**, handed to another agent with its own design and plan, as the NES's were. The 2600 is cased, so it gets two models, the outside and the board, and the registry rules stop it claiming one. Models never hold up a count (Dan, 2 October). This machine's host exposes nothing for them in its first pull request.

## Tasks

Sizes are in agent tasks, each built by a fresh agent and reviewed, against two yardsticks: the BBC Micro's plan had 15 tasks and the NES's 16, and the NES's lazy chips plan 6 more. **S** is a task like the NES's task 7 (DMA and the controllers), **M** like its task 2 (the region, the cartridge and NROM) or task 13 (the homebrew and the acceptance test), and **L** like its task 5 (the PPU draws).

| 2 | The region, the cartridge and the five boards, with their refusals | M |

## Risks

- **The suite may be wrong.** It is young and was "verified" on one console. A trusted test that fails is triaged against the TIA documents before the model is changed to suit it, and the trust split above is the line.
- **TIA behaviour varies between chips.** Some HMOVE effects differ from console to console. The model is one console's behaviour, and the page and `known-differences.md` say which.
- **The suite's binaries live in a second repository.** The README's path to them has moved. Task 1 assembles the pinned sources once, locally, with DASM, and compares hashes with the prebuilt files, and the journal says what matched.
- **Speed.** The browser figure may be thin before the speed pass, as the NES's was. The milestone measures it before sound and input are built.
- **Board by size.** An 8K or 16K game made for another board fails to run. The page says so.
- **The bundled game's first picture.** Core Escape has not been run here. If it needs input or does not draw, the fallback is above.

## How the work lands

- **Spec and plan** in `docs/superpowers/` in this repository, the plan with every code block compiled and run before it goes in.
- **Build** with a fresh agent per task, each reviewed before the next starts.
- **Journal** an entry per working day in `docs/journal/`, in the same pull request as the work (rule 6).
- **Pull requests:** one for the machine, the host and the page; a second for the speed pass; a third for the models. Nothing merges until `Validate` is green, and the live count changes only with Dan's go.
- **Rights:** `roms/README.md` gets the bundled game's entry. `AGENTS.md`'s layout and `docs/known-differences.md` are updated as the code arrives.

## Out of scope

SECAM, the boards and controllers listed above, the Atari 7800's 2600 mode, the 2600+ of 2023 and other re-creations, and the single-chip 6591 and 6592 consoles, which are separate rows if they are ever built. The 3D models and the speed pass are in scope, as later pull requests.
