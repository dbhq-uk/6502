# 6502: design

Written 29 September 2026. Stage 1 (the core) is specified in full. Stages 2
to 6 are outlined here and each gets its own spec when it starts.

## What this is, and where it is going

A cycle-accurate 6502 core in C# on .NET 10, covering both the original NMOS
6502 and the CMOS 65C02, then the machines built on it: the KIM-1 first, then
the BBC Micro, then the NES. It is built in public. This repository holds the
design, the plan and the code, and the journey is written up at 6502.dbhq.uk.

The end goal is a verified port of *Mega Man 2* (NES, 1988), checked against
the original by differential testing: run the original's own instructions on
the emulator, run the port beside it from the same starting bytes, and compare
every byte of memory and video on every pass. A difference is a
number, not an argument. That needs an NES that is accurate enough to be
trusted as the reference, which needs a cycle-accurate 6502 under it.

The NES emulator is also a product in its own right, not only scaffolding for
the port. It is held to the community accuracy test ROMs, not only to what
one game needs.

*Mega Man* is a trademark of Capcom Co., Ltd. This project is not affiliated
with, endorsed by or sponsored by Capcom. The port itself, and anything of
Capcom's (the ROM, its graphics, music and code), is never in this repository
and never on the site. The port lives in a separate private repository.

## The order, and why

1. **The core.** Nothing else can be trusted until this is proven.
2. **The site, and a browser speed check.** Runs alongside the core.
3. **KIM-1.** MOS Technology's own 1976 board, built to show engineers the
   6502: a hex keypad, six LED digits, 1 KB of RAM and one new chip, the
   6530. It is first light, the core running real software in a browser
   within days of passing its tests rather than weeks, and a machine small
   enough that when something is wrong, the fault is in the core or in one
   chip.
4. **BBC Micro Model B.** A simpler machine than the NES: no picture
   processor to get exactly right, and a large, well-documented body of
   software to test against. It proves that the core really is shared and
   that a whole machine of several chips can be built on it.
5. **NES.** 2A03 (the CPU with its sound unit), PPU (the picture chip),
   mappers, then the accuracy test ROMs.
6. **The port.** Private, differential testing against the emulator, its own
   repository and spec.

Other 6502 machines, the VIC-20 for example, may follow. They are different
machines rather than different ROMs: each has its own video chip, sound chip
and memory map, so each is a project of its own, sharing only the core. The
whole family, and which of it the core can run, is in
[`docs/the-6502-family.md`](../../the-6502-family.md).

## Stage 1: the core

### Shape

One C# class library. No dependencies. No knowledge of any machine.

```csharp
public interface IBus
{
    byte Read(ushort address);
    void Write(ushort address, byte value);
}
```

**Every bus access is one cycle.** The 6502 does exactly one read or one write
on its bus every clock cycle. The core is written as plain instruction code
where each `Read` and `Write` is one cycle, and the machine's implementation of
those two calls advances every other chip by one cycle before returning. Time
moves forward exactly when the real CPU would use the bus, so a cycle cannot
be forgotten: a cycle is a bus access. A reviewer counts an instruction's
cycles by counting its `Read` and `Write` calls.

Two alternatives were considered and rejected:

- **An explicit per-cycle state machine** is no more accurate, about three
  times the code, and much harder to read. Its one advantage, pausing between
  any two cycles from outside, is not needed by an emulator.
- **A transistor-level model** is correct by definition but runs thousands of
  times too slowly to play anything. It is used as a referee only, to generate
  the expected results for the interrupt tests below. It never ships.

### Parts

**The CPU.** Registers `A`, `X`, `Y`, `S` (stack pointer), `P` (flags) and
`PC`. `Step()` runs one whole instruction, two to seven bus calls. The 256
opcodes are one `switch`. Addressing modes are shared helpers, and each spells
out its dummy reads line by line. A dummy read is a read whose result the chip
discards. It is harmless on RAM and not harmless on a hardware register, where
a read can clear a flag or advance a counter, so real software depends on them.

**Interrupt lines.** The machine drives `Nmi`, `Irq` and `Reset`, as the real
chips pull pins. When an interrupt lands follows the transistor-level model,
which was run against the core before the plan was written:

- An instruction takes an interrupt that became active by the end of its last
  cycle, with the line changed at the start of a cycle. Descriptions that say
  "the second-to-last cycle" count from a different point in the cycle.
- A taken branch that stays on its page decides at its operand cycle, so an
  interrupt that arrives on its last cycle waits for one more instruction.
- An NMI that arrives by the time `BRK`, or an IRQ, pushes P takes it over;
  one that arrives while the low byte of the vector is read is lost; one that
  arrives on the high byte waits until the handler's first instruction has
  run.
- `CLI`, `SEI` and `PLP` change the interrupt-disable flag one instruction
  late.

**Stalls.** The NES freezes the CPU to copy data by DMA, and the BBC Micro
stretches accesses to slow devices to line up with a 1 MHz clock. Both live in
that machine's `Read` and `Write`, which tick extra cycles before returning.
The core needs no special code.

**Variants.** The CPU is constructed as one of five variants, each checked
against its own test set:

| Variant | Chip | Used in |
|---|---|---|
| `Nmos6502` | The original MOS 6502 and its cut-down versions | KIM-1, BBC Micro, Apple II, Commodore 64, Atari 2600 and 8-bit |
| `Ricoh2A03` | The NMOS 6502 with decimal mode removed | NES, Famicom |
| `Synertek65C02` | CMOS, also called the 65SC02: adds `PHX`, `PHY`, `PLX`, `PLY`, `STZ`, `TRB`, `TSB` and a zero-page indirect addressing mode | The 65SC02 family, which the BBC Master's 65SC12 belongs to |
| `Rockwell65C02` | All of the above, plus the bit instructions `BBR`, `BBS`, `RMB` and `SMB` | Rockwell-based designs |
| `Wdc65C02` | All of the above, plus `WAI` (wait for an interrupt) and `STP` (stop the clock) | Every modern 6502 machine, because WDC's is the one still made |

The 65C02 is not only new instructions. It fixes the NMOS chip's quirks, and
each fix changes timing, so each is written out and tested:

- `JMP ($xxFF)` reads its target across the page boundary correctly, and takes
  one cycle longer to do it.
- In decimal mode the flags are correct, and `ADC` and `SBC` take one extra
  cycle.
- An interrupt clears the decimal flag.
- A read-modify-write instruction reads twice and writes once, where the NMOS
  chip writes the old value back before the new one.
- An indexed read that crosses a page re-reads a different address as its
  dummy read.
- Every opcode the NMOS chip left undocumented is a defined no-op on the 65C02,
  each with its own length and cycle count. None of the NMOS undocumented
  behaviour survives.

**Decimal mode.** `ADC` and `SBC` work in binary-coded decimal when the flag is
set. On the NMOS chip that includes its flag quirks and its repeatable answers
for invalid digits; the 65C02 variants use the corrected behaviour. The
`Ricoh2A03` variant has no decimal mode, because the NES's 2A03 had it removed.

**Undocumented opcodes, on the NMOS variants.** All 105. The stable ones (`LAX`, `DCP` and others)
are used by real software on both machines. The unstable ones (`ANE`, `SHA` and
others) vary between individual chips; the core matches the test data and the
documentation says so rather than claim one answer. The twelve `JAM` opcodes
lock the CPU until reset, and the core reproduces the lock.

**Disassembler and tracer.** Neither affects behaviour. The tracer writes the
Nintendulator log line format used by `nestest`, so a run can be compared on program counter, instruction bytes, mnemonic and undocumented mark, A, X, Y, P, SP and cycle count; operand text is not compared.

### How the core is proven

Five layers. Each catches something the others cannot.

1. **Tom Harte's SingleStepTests** (`SingleStepTests/65x02`, MIT). For each of
   the 256 opcodes, 10,000 cases give the state before, the state after, and
   the full bus log: address, value and read or write for every cycle. Five
   sets are used, one per variant: `6502`, `nes6502`, `synertek65c02`,
   `rockwell65c02` and `wdc65c02`. About 2.5 million cases each. The WDC set
   leaves out `WAI` and `STP`, which cannot be tested one instruction at a
   time; they get tests of our own under layer 3. The core's `Read` and
   `Write` are logged and the log is compared cycle by cycle. This catches
   wrong results, wrong flags, wrong cycle counts, missing or extra dummy
   reads, and misordered writes. It cannot catch anything spanning more than
   one instruction, or interrupts. The data is not committed: the tests
   download it on first run, pinned to commit `2f6980a`, and check each file
   against its git blob hash from that commit. One narrow exception, recorded
   in [`docs/known-differences.md`](../../known-differences.md): on the three
   65C02 variants, the address and value of the extra decimal-mode cycle of
   `ADC #imm` and `SBC #imm` are not compared, because the data records a
   fixed address there that looks like an artefact of how it was generated.
2. **Klaus Dormann's functional tests** (GPL-3.0): a whole program that checks
   its own results across every official instruction and addressing mode, a
   second for decimal mode across every input, and a third for the 65C02's
   added instructions, built once per 65C02 variant. It loops at a known address
   on success and at the failing address on failure. This catches bugs that
   only appear when instructions run in sequence. It is downloaded at test
   time and never committed, because this repository is MIT.

   Only two of the builds needed come assembled, so the rest are assembled
   at test time with Dormann's own assembler, `as65`, from the same pinned
   commit. It is a 32-bit Linux program and needs the `libc6-i386` and
   `lib32stdc++6` packages. **These tests run on Linux, in CI and locally.**
   On Linux a missing package fails the test with the command that installs
   it; on Windows and macOS the tests are skipped and say why. The done
   criteria below are judged on CI. The builds:

   | Program | Variants | Settings |
   |---|---|---|
   | Functional test | NMOS 6502, the three 65C02s | As shipped |
   | Functional test | 2A03 | `disable_decimal = 1` |
   | Decimal test | NMOS 6502 | `cputype = 0`, every flag checked |
   | Decimal test | the three 65C02s | `cputype = 1`, every flag checked, assembled with `-x` |
   | Extended test | WDC, Rockwell | `wdc_op = 1`, `rkwl_wdc_op = 1`, `-x` |
   | Extended test | Synertek | `wdc_op = 1`, `rkwl_wdc_op = 2`, `-x`: the bit-instruction opcodes are left out, because this test and Harte's data disagree about them; see [`docs/known-differences.md`](../../known-differences.md) |

   The decimal test ends on a 65C02 `STP`, which is not an instruction on the
   NMOS chip, so its `end_of_test` macro is replaced with `jmp *`. **Only
   65C02 builds get `-x`,** because that switch also rewrites `jmp *` as the
   65C02's `BRA`, which is a two-byte no-op on the NMOS chip. The success
   address is read from the assembler's listing.
3. **Interrupt timing tests**, our own. Neither of the above covers
   interrupts. A harness drives the Visual6502 transistor-level model through
   134 short runs, raising IRQ or NMI on a chosen cycle around ordinary
   instructions, branches on and across a page, `BRK`, `CLI`, `SEI` and
   `PLP`, and records the bus log of each. The core must match every cycle,
   so the answer is the chip's rather than a reading of a document. The 65C02 adds its own cases: the decimal flag
   cleared on an interrupt, `WAI` waking on one, and `STP` stopping until
   reset. There is no public transistor-level model of the 65C02, so their
   expected logs come from WDC's datasheet, and the tests say so.
4. **`nestest`**, NMOS only: a known-good instruction trace, about 8,900 lines including
   undocumented opcodes, compared on program counter, instruction bytes, mnemonic and undocumented mark, A, X, Y, P, SP and cycle count; operand text is not compared. The first
   differing line is reported.
5. **Speed**, as a local benchmark rather than a gate, because CI runners vary
   too much to fail a build on. The target is at least 25 times real speed for
   the core alone, so that a whole machine sharing each cycle with its video,
   sound and timer chips still keeps up.

**The core is done when** all Harte cases pass in all five sets, every
Dormann program reaches its success address for every variant it applies to, the `nestest` trace matches to the last
line, and every interrupt test passes. Nothing skipped.

## Stage 2: the site, and the browser speed check

**Speed check first.** As soon as the core passes Harte, run Dormann's program
in the browser two ways: .NET's interpreter mode, which Blazor uses by
default, and compiled ahead of time to WebAssembly. Record cycles per second. A
BBC Micro needs about 2 million a second with headroom. This settles the
browser question while a change of course is still cheap.

**The site** is a journal of the journey at 6502.dbhq.uk: dated entries at each
milestone saying what was built, what went wrong and why, and the numbers at
that point. It is an Astro site, like the other DBHQ sites, so it inherits
their content tests. The emulators run in the browser as Blazor WebAssembly
apps loaded into their pages.

- **Figures are never typed by hand.** CI writes the test results to a file and
  the site reads that file. A page quoting a figure the file does not contain
  fails the build. A hand-kept count drifts from the truth without anyone
  noticing, and a build-in-public site with a wrong number is worse than
  none.
- **It goes live as soon as there is something true to show:** the first entry
  and the live Harte figures, even partial. Early, unfinished numbers are part
  of the story.
- **Where it lives.** Site source in this repository under `site/`. DNS, the
  Cloudflare Pages project and its state in `infra/6502/` in `dbhq-uk/dbhq`,
  with every other Cloudflare resource in the zone. That is the `terraken`
  split, for the same reason: the site reports what the tests produce, so the
  build must be able to fail when the site claims something the tests do not
  back. Across two repositories that check cannot exist.
- **The look** goes through the `impeccable` skill against the DBHQ brand, in
  that stage's own spec.
- **System ROMs and games.** Every machine boots from its maker's own ROM
  (Acorn's MOS and BBC BASIC, Commodore's KERNAL). Serving one from a public
  page needs permission or a clear free licence, checked per machine before its
  page ships. The fallback is that the page asks the visitor for the file. The
  site bundles homebrew and freely licensed software only. Commercial games
  are load-your-own, and *Mega Man 2* never appears on the site.

## Stages 3 to 6, outlined

**Stage 3, KIM-1.** A 6502, 1 KB of RAM, two 6530s (each a combined ROM, RAM,
I/O and timer chip), a hex keypad and six seven-segment LED digits. The CPU
lights the digits one at a time, fast enough to look steady, so the page
models how long each digit stays lit. Before any code, a `legwork` check on
whether the KIM-1 monitor ROM can be served publicly; its full listing was
printed in the KIM-1 manual, and MOS Technology later became part of
Commodore. Its spec decides the finish line; the likely one is the monitor
running in the browser with the keypad working, and a program of the period
running on it.

**Stage 4, BBC Micro Model B.** Before any code, a `legwork` check on whether
Acorn's ROMs can be served publicly. Its spec decides the finish line; the
likely one is booting to the BASIC prompt and passing community timing tests.

**Stage 5, NES.** Done is measured by the standard community test ROMs, with
pass counts from CI on the site. Its spec chooses the accuracy target and the
mapper list. *Mega Man 2* uses MMC1, so that mapper is required.

**Stage 6, the port.** Private repository, differential testing: the emulator
is the reference, the port runs beside it, and every pass compares memory and
video. A written legal-position note comes before the repository exists. It is
not legal advice and says so.

## How work lands

- Every change goes through a pull request and merges when `Validate` is green.
  A red `main` is visible to everyone in a public repository that deploys a
  site.
- The `Validate` workflow runs the whole test suite. Third-party test data and
  programs are downloaded by the tests, pinned and hash-checked.
- **The journal is drafted from commits and test output** at each milestone,
  given a `verve` pass, and goes to Dan as a pull request. It is published only
  when he merges it.

## Decisions taken while writing this

| Decision | Chosen over | Why |
|---|---|---|
| Public repository from the first commit | Private until stage 1 was done | Dan asked for build in public |
| The NES emulator is a product in its own right | An oracle for the port only | Dan's answer; it raises the bar to the accuracy test ROMs |
| BBC Micro before NES | NES straight away | Dan's answer; a simpler machine proves the shared core first |
| The 65C02 is part of the core, all three variants Harte tests | A Commodore 64 between the BBC Micro and the NES; the 65C02 left for later | Dan's call. It opens the BBC Master, the later Apple IIs and every modern 6502 machine, and it is proven the same way as the NMOS core |
| KIM-1 before the BBC Micro | BBC Micro as the first machine, Apple I, Apple II | First light in days rather than weeks, and a fault can only be in the core or one chip |
| Every bus access is one cycle | Per-cycle state machine, transistor netlist | Same accuracy as the first, a third of the code, checked directly by Harte's bus logs |
| Design lives in this repository | `dbhq-uk/dbhq`, which is private | The design is chapter one of the public journey |
| *Mega Man 2* named in public, with a non-affiliation line | Silence until the port starts | Dan's decision |
| Keep Dormann's assembler, on CI and Linux only | Drop it and run the two prebuilt programs | Dan's call, 30 Sep. Keeps the only exhaustive decimal test and the whole-program runs on the 2A03, Rockwell and Synertek, at the cost of two 32-bit packages and a Linux-only part of the suite |
| Leave the Synertek bit-instruction opcodes out of Dormann's extended test | Follow Dormann there and make a second exception to Harte's data | Harte is the per-instruction authority; Dormann's test has a setting for exactly this. Found while proving the plan, 30 Sep |
| Do not match the fixed address in the 65C02's decimal immediate cycle | Match Harte's data exactly | Matching it would build a test-data artefact into the emulator; the exception is one cycle wide and written down |
| Site at 6502.dbhq.uk, source here, infrastructure in `dbhq-uk/dbhq` | Everything in one repository | The `terraken` split |

## Out of scope for this spec

Stages 2 to 6 in any detail, CPUs beyond the 65C02 (the 65C816, the HuC6280,
the 65CE02 family),
sound quality beyond what the accuracy tests measure, and any mobile or native
frontend. Each is a later spec if wanted.
