# Acorn Electron: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Acorn Electron on the core: it boots OS 1.00 to the BBC BASIC prompt, runs a BASIC program, saves it to a UEF tape image and loads it back, shows the contention the ULA puts on the CPU, and runs in the browser at 6502.dbhq.uk, as the design in [`../specs/2026-10-04-electron-design.md`](../specs/2026-10-04-electron-design.md) says.

**Architecture:** A new library `Dbhq.Machines.Electron` on the `Nmos6502` core. An `ElectronBus` implements `IBus`; every `Read` or `Write` is judged by its address and takes the number of 2 MHz cycles the ULA's rule gives it (one for ROM, two or three for RAM and I/O, more while the ULA holds the CPU off in modes 0 to 3). The ULA is split into files that each do one job, written from the fact sheets in [`docs/electron/facts/`](../../electron/facts/README.md), never from another emulator's code. The ULA's slow work (the picture, the sound, the tape) is caught up lazily at events and never ticked per cycle, as the BBC's chips are; only the contention answer is asked on every access. The browser host (`machine-host.js`) already exists and is reused.

**Tech Stack:** C# on .NET 10, xUnit 2.9.3 (the versions the BBC tests use), .NET WebAssembly compiled ahead of time for the browser, plain JavaScript modules and an `AudioWorklet` for the page, Astro for the site, Playwright for the real-browser check.

**This plan has NOT been pre-run the way the stage 1 plan was**, and the BBC plan was not either. The ULA is thousands of lines, so its code is not written into the plan. Each task states its interfaces, the facts it is built from, and the exact test assertions; the implementer writes the tests first and the code to pass them, and a reviewer gates each task. Where a number is fixed by the sheets, the test is written here in full (the contention table, the CRC vector, the tape block, the UEF round trip). What is proven early is the risky part: task 5 boots the real OS headless, task 6 puts the contention in and checks it against seven real-hardware timings, and task 7 measures the speed in a browser with that check on every access.

## Global Constraints

- **Every bus access is a whole number of cycles, and each is judged by the address on the bus in that cycle.** ROM is 1 cycle. RAM and the ULA's registers are 1 MHz accesses: 2 cycles if the previous bus cycle ended on a 1 MHz boundary and 3 if not. In modes 0 to 3 a RAM access that falls in the display window of a contended line waits for the window to end. The core's **dummy reads and the second write of a read-modify-write reach the bus and are judged like any other** (`ula.md` s4g: leaving the dummy stack read out of `RTS` and `RTI` made a model run 1.4% to 1.7% fast in every mode). (`AGENTS.md` rule 1; design "Contention".)
- **The core knows no machine.** Nothing under `src/Dbhq.Cpu6502/` names the Electron. (Rule 2.)
- **No code from another emulator.** Elkulator, elkjs, ElectrEm, jsbeeb and B-em are GPL or have other terms, and this repository is MIT. Parts are written from the fact sheets. Only the ROMs are taken from outside. (Design "Where the code comes from".)
- **System ROMs are committed under `roms/`** with where they came from and what is known of their rights in `roms/README.md`, checked against a SHA-256 pinned in `Pins.cs` every time they are read. The Electron's operating system goes in `roms/electron/os.rom`. **BASIC is the BBC's file** (`roms/bbc-micro/BASIC.ROM`, hash `45bd55dc0f6f0f8f1fe9e2481de7def206565eec8f600ba3068b849ca4132079`) and is kept once. (Rules 3 and 4.)
- **Games and commercial tapes are never committed.** The page takes a `.uef` the visitor drops on it. Tape images the tests use are written by the machine under test or by the test itself. (Rule 3.)
- **Nothing depends on a third party's server.** `site/tests/mirrors.test.mjs` fails on any fetch from outside `dbhq-uk`. No test needs the network. The one fetch this plan makes (task 1) is of the ROM, once, and it is committed.
- **No figure describing the project as it stands is typed by hand.** The home page count and every pass count come from the registry and the test results. (Rule 5.)
- **The expected numbers in a test come from the fact sheets or from arithmetic anyone can redo, never from running the model.** A test says which sheet section its number is from. (`ula.md` s11.)
- **Document as you go.** Each task ends by adding to that day's journal entry in `docs/journal/`: what was built, what the tests showed, what surprised, and any decision with what it was chosen over. A difference from a reference also goes in `docs/known-differences.md`. (Rule 6.)
- **The page says what is not modelled:** the Plus 1 and its cartridge slots, the Plus 3 and its disc controller, the joystick and printer ports, 300 baud tapes and non-standard tape formats. (Design, "What is left out"; `tape.md` s6.)
- **Namespace `Dbhq.Machines.Electron`**; projects `src/Dbhq.Machines.Electron/`, `src/Dbhq.Machines.Electron.Wasm/`, `tests/Dbhq.Machines.Electron.Tests/`; all in `6502.slnx`.
- **Warnings are errors** (`Directory.Build.props`: `net10.0`, nullable, implicit usings, `TreatWarningsAsErrors`).
- **British English, and no em or en dashes** in code, comments, docs and the site. CI checks the dashes.
- **The site's copy rules hold:** headings carry no trailing full stop, a journal summary shows no typed machine numbers (the home page test reads them as figures; learned in [PR #49](https://github.com/dbhq-uk/6502/pull/49)), and `site/tests/` has its own content checks, which must pass.
- **Git:** all work is on branch `feat/electron`, one commit per task with a conventional-commit message, pushed after each. A draft pull request is opened after task 1 so `Validate` runs on every push, and marked ready after task 14. It is merged only when `Validate` is green and Dan says so, because merging deploys and changes the live count. The 3D models are a separate branch and a separate plan.
- **Stay on the branch.** Never switch, create or move to another branch or worktree except as this plan says.

## Review Focus

The five inputs the spec implies and no task's happy path exercises, most likely to bite first. Each has a test in the task that owns the code.

1. **A tape image that is damaged or not what it says.** A gzip stream cut short, a chunk whose length runs past the end of the file, a header that is not `UEF File!`, a zero-length file. A person who drops the wrong file expects a sentence saying what is wrong and the machine untouched, not a hang or an exception in the console. (Task 11.)
2. **A tape the first version does not load**: chunk `&0117` set to 300, `&0104` or `&0102` carrying data, `&0113` not 1200 Hz, a major version above 0. A person expects it to be refused by name, not to be loaded as noise. (Task 11.)
3. **BREAK in the middle of things.** A soft BREAK must keep RAM and leave the machine at the prompt without the bell glyph; CTRL-BREAK differs; BREAK while a ROM other than slot 8 to 11 is paged must still reach BASIC; BREAK while the tape motor is on must stop the tape. A person expects BREAK to always get them back. (Tasks 5, 12.)
4. **Several keys held at once, and the one key that is two.** The matrix returns the OR of every selected column, both Shift keys are one position, and Caps Lock and Func are one key. A person typing fast expects every key to register and no phantom key. (Task 4.)
5. **Anything that happens at a frame or field boundary.** A RAM access that starts before display end and finishes after it, a mode change in the middle of a field, an interrupt while the CPU is held off. A person expects the picture not to tear and the program not to stall for a frame. (Tasks 6, 8.)

## Facts every task relies on

Read these once; each task names the sections it needs.

- OS **1.00**; BASIC in slots 10 and 11 (one chip, both slots); the keyboard is slots 8 and 9 and is hardware, not an image. `ula.md` s2.
- Reset vector `$D8D2`; NMI `$0D00`; IRQ `$DAE7`. `ula.md` s1a.
- **A frame is 80,000 cycles**: an odd field of 312 lines (39,936 cycles) and an even field of 313 lines (40,064 cycles), 128 cycles a line. RTC interrupt at 12,670 and 52,670. Display end at 32,736 and 72,672 (modes 0, 1, 2, 4, 5), and at 31,968 and 71,904 (modes 3 and 6). `ula.md` s5d.
- The boot screen, mode 6, 40 columns by 25 rows at `$6000`, 320 bytes a character row: row 0 blank; row 1 `Acorn Electron ` and a bell glyph (`18 3C 3C 7E 7E 00 7E 3C`) in column 15; row 2 blank; row 3 `BASIC`; row 4 blank; row 5 `>`. About 0.66 s after reset. The bell glyph is drawn on power on and CTRL-BREAK only, not on a soft BREAK. `ula.md` s10b.

### Task 2: The bus, the memory map, ROM select and the per-access cost, without contention

**Files:**
- Create: `src/Dbhq.Machines.Electron/ElectronBus.cs`, `ElectronTiming.cs`
- Test: `tests/Dbhq.Machines.Electron.Tests/ElectronBusTests.cs`, `ElectronTimingTests.cs`

**Interfaces:**
- Consumes: `ElectronRoms` (task 1), `IBus` (core).
- Produces:
  ```csharp
  public enum AccessKind { Rom, Ram, Io }
  public static class ElectronTiming
  {
      /// The time at which an access that starts at `start` (in 2 MHz cycles since power on) completes.
      /// ula.md s4b. Contention is added in task 6; until then `mode` is ignored.
      public static long Complete(long start, AccessKind kind, int mode);
  }
  public sealed class ElectronBus : IBus
  {
      public ElectronBus(ElectronRoms roms, int sampleRate = 44100);
      public long Cycles { get; }                 // 2 MHz cycles since power on, wait cycles included
      public int RomSlot { get; }                 // the paged ROM select, 0 to 15
      public byte Read(ushort address);
      public void Write(ushort address, byte value);
      public byte Peek(ushort address);           // no cycle, no side effect; for tests and debuggers
      public void PokeRam(ushort address, byte value);   // for tests: loads RAM without a cycle
      protected internal virtual void Tick();     // one cycle for the lazy parts; empty until later tasks
  }
  ```
  Later tasks add `Ula`, `Keyboard` as properties and decode them from the one place `ReadSheila(int offset)` / `WriteSheila(int offset, byte value)`, so each task adds a `case`.

**What it must do (`ula.md` s1, s2, s3a, s4b):**
- `$0000-$7FFF` RAM, 32 KB, **no aliasing**. Writes to ROM are ignored. `$8000-$BFFF` is the paged window chosen by `RomSlot`: slots 10 and 11 read `basic.rom`; slots 8 and 9 read the keyboard (task 4; until then `$00`); every other slot reads the high byte of the address (an empty slot: `ula.md` s12 item 3 recommends this and the boot does not depend on it). `$C000-$FBFF` and `$FF00-$FFFF` read the OS ROM. `$FC00-$FEFF` is I/O, never ROM.
- **ROM select, `$FE05` (`ula.md` s2a):** bits 3 to 0 are the slot. If the slot now paged in is 8 to 11, a write is honoured **only if its bit 3 is set**; otherwise any write is honoured. A write of `$0C` to `$0F` selects that slot and makes the register accept a second write that can select any slot. Bits 7 to 4 are interrupt clears (task 3): they do not affect the select. Power-on slot is 0 (`ula.md` s12 item 4: not established; the OS writes `$F8` first).
- **Cost (`ula.md` s4b, with the display window left out):** with `T0` the time the previous bus cycle ended, a **ROM** access (A15 set, not `$FC00-$FEFF`, not the keyboard) completes at `T0 + 1`. A **RAM** (A15 clear) or **I/O** (`$FC00-$FEFF`, slots 8 and 9) access completes at the first even time that is at least `T0 + 2`: **2 cycles if `T0` is even, 3 if odd**. Judge every bus cycle by its own address, dummy reads and read-modify-write double writes included.
- `Cycles++` happens in the one place that runs a cycle, so no cycle is counted without an access, and `Tick()` is called once per elapsed cycle only where a later task needs it.

### Task 3: The ULA's registers, the frame and the interrupts

**Files:**
- Create: `src/Dbhq.Machines.Electron/Ula.cs`
- Modify: `ElectronBus.cs` (decode `$FE00-$FEFF` into the ULA, mirrored every 16 bytes; call the ULA's catch-up)
- Test: `tests/Dbhq.Machines.Electron.Tests/UlaInterruptTests.cs`

**Interfaces:**
- Produces:
  ```csharp
  public sealed class Ula
  {
      public int Mode { get; }                       // $FE07 bits 5 to 3, with 7 acting as 4 (ula.md s5a)
      public byte Status { get; }                    // what a read of $FE00 gives, including the power-on flag rule
      public bool Irq { get; }                       // an enabled source is set
      internal long NextEvent { get; }               // the next cycle at which something happens; the bus compares one long per access
      internal void CatchUp(long cycle);             // raises the RTC and display-end interrupts due by `cycle`
      internal void Write(int register, byte value); internal byte Read(int register);   // register 0 to 15, already mirrored
  }
  ```

**What it must do (`ula.md` s1c, s5d, s6):**
- Registers as `ula.md` s1c: `$FE00` write is the interrupt enable (bits 6 to 2 only), read is the status (bit 7 always 1, bit 0 the master IRQ, bit 1 the power-on flag, bits 6 to 2 the five sources). Registers repeat through all of `$FE00-$FEFF`. `$FE07` bits 5 to 3 hold the mode; a mode value of 7 acts as mode 4.
- **The status bits are set whether or not the interrupt is enabled**; the enable only gates bit 0 and the IRQ line (`ula.md` s6a).
- **The power-on flag** is set at power on and cleared by the first read of `$FE00`; BREAK does not set it (`ula.md` s6a, s10a: the OS tells them apart by it).
- **The frame** (`ula.md` s5d), times in 2 MHz cycles from power on: odd field 0 to 39,935, even field 39,936 to 79,999. **RTC** interrupt at 12,670 and 52,670 of each frame. **Display end** at 32,736 and 72,672 in modes 0, 1, 2, 4, 5, and at 31,968 and 71,904 in modes 3 and 6 (the mode in force at that moment). Clear by writing 1 to `$FE05` bit 5 (RTC), bit 4 (display end), bit 6 (high tone), bit 7 (NMI: nothing in the ULA to clear).
- **The CPU's IRQ line** is `Irq` and is set into `Cpu.Irq` by the machine after each step (task 5); no NMI source of its own (`ula.md` s6a).
- `NextEvent` makes this lazy: the bus does `if (Cycles >= _ula.NextEvent) _ula.CatchUp(Cycles)` once per access and the ULA does its work only at events.

- [ ] **Step 1: Failing tests** (`UlaInterruptTests.cs`). With a bus and the ULA alone (no CPU), set `Cycles` by calling `CatchUp` directly and assert, in order:
  - The status read after power on has bit 7 and bit 1 set; the second read has bit 1 clear.
  - With nothing enabled, run to 12,670: status bit 3 (RTC) is set and bit 0 (master IRQ) is not. Enable bit 3 by writing `$08` to `$FE00`: bit 0 sets and `Irq` is true. Write `$20` to `$FE05`: bit 3 clears and `Irq` is false.
  - RTC fires at 12,670 and again at 52,670 (exactly 40,000 apart), and a third time at 92,670 (the next frame).
  - Display end fires at 32,736 and 72,672 in mode 4 (write mode 4 to `$FE07` first). In mode 6 it fires at 31,968 and 71,904. Setting the mode between two frames changes only the later firing.
  - The two display ends are 39,936 apart, not 40,000 (`ula.md` s5d: "40,000 plus or minus 64"): assert 72,672 - 32,736 == 39,936.
  - A write of `$10` to `$FE05` clears display end only. A write of `$40` clears high tone only.
  - Writes to `$FE00` bits 1, 0 and 7 have no effect on the enable.
  - A register accessed at `$FEA2` is the same as `$FE02` (mirroring).
- [ ] **Step 2: Run them: fail. Step 3: Implement `Ula`** and its decode in the bus. **Step 4: PASS** and the whole project.

**What it must do (`tape.md` s4, s5, with task 10's findings written into the sheet):**
- **Input** (`$FE07` bits 2 and 1 = `00`, motor bit 6 set): the tape advances in CPU cycles. `Carrier(n)` takes `n x 832` cycles; **high-tone-detect (status bit 6)** is set after ten bit times (16,640 cycles) of carrier and cleared by a write of `$40` to `$FE05`. Each `TapeByte` takes ten bit times (16,640 cycles); **receive-full (status bit 4)** is set nine bit times in (14,976 cycles) with the byte in `$FE04` and cleared by reading `$FE04`. A byte not read within about 2 ms (4,000 cycles) is lost (`ula.md` s9). `Silence` advances time and delivers nothing. At the end of the tape nothing more is delivered.
- **Output** (`$FE07` bits 2 and 1 = `10`, motor on): a write to `$FE04` clears transmit-empty (status bit 5) and **sets it again nine bit times later**; the byte is recorded as `TapeByte` and the time between one byte's end and the next byte's write, **when it is longer than one bit time**, is recorded as `Carrier(idleCycles / 832)` (the rule `tape.md` s7 item 2 expects; **follow task 10's finding if the OS makes carrier another way**).
- **Motor off, or neither mode:** the tape does not move and records nothing.
- Everything is event-driven and lazy: the next tape event goes into `NextEvent`, so the CPU's loop pays one comparison.
