# The NES: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Nintendo Entertainment System, NTSC and PAL, on the core: it passes `nestest` and the chip tests, passes the pinned community test ROMs except where a failure is written down, boots a freely licensed homebrew game to its recorded picture, and runs in the browser at 6502.dbhq.uk with picture, sound and controller input, as the design in [`../specs/2026-10-05-nes-design.md`](../specs/2026-10-05-nes-design.md) says.

**Architecture:** A new library `Dbhq.Machines.Nes` on the `Ricoh2A03` core. A `NesBus` implements `IBus`. Every `Read` or `Write` is one CPU cycle, and it advances the PPU by the region's dot ratio (3 dots a cycle on NTSC, 16 dots in 5 cycles on PAL) and the APU by one cycle. A `Region` value holds every number that differs between NTSC and PAL, so no chip tests for a region by name. Each chip is one class in its own file, tested alone, written from the fact sheets in `docs/nes/facts/` and never from another emulator's code. The shared browser host from the BBC Micro's work runs the page.

**Tech Stack:** C# on .NET 10, xUnit 2.9.3 (the versions the other test projects use), .NET WebAssembly compiled ahead of time for the browser, plain JavaScript modules and an `AudioWorklet` for the page, Astro for the site, headless Chrome for the real-browser check.

**This plan has NOT been pre-run the way the stage 1 plan was.** The PPU and APU are thousands of lines, so their code is not written into the plan. This is the form the BBC Micro's plan took, and for the same reason. Each task states its interfaces, the facts it is built from, and the exact test assertions. The implementer writes the tests first and the code to pass them, and a reviewer gates each task. What is proven early is the risky part: task 3 runs `nestest` through the real bus, whose log also checks the PPU's dot counter, and task 6 measures the speed in a browser before the sound and the mappers exist.

**Spec:** [`docs/superpowers/specs/2026-10-05-nes-design.md`](../specs/2026-10-05-nes-design.md). The 3D models are **not** in this plan. They are a second pull request, with their own design and plan, written by another agent on branch `feat/nes-models`.

## Global Constraints

- **Every bus access is one cycle.** `NesBus.Read` and `Write` are one CPU cycle each, and advance the other chips inside the call. A DMA stall is the bus taking more cycles inside a call before it returns. (`AGENTS.md` rule 1; spec "Parts".)
- **The core knows no machine.** Nothing under `src/Dbhq.Cpu6502/` names the NES. (Rule 2.)
- **No code from another emulator.** Mesen, FCEUX and Nestopia are GPL and this repository is MIT. The chips are written from the nesdev wiki, through the fact sheets, each of which names the wiki page every statement comes from. (Spec "Where the code comes from".)
- **Nothing depends on a third party's server.** Test ROMs come from the existing fork `dbhq-uk/nes-test-roms` at a pinned commit, each with a recorded hash in `Pins.cs`. The bundled homebrew is committed under `roms/nes/` with its provenance in `roms/README.md`. `site/tests/mirrors.test.mjs` fails on any other host. (Rules 3 and 4.)
- **Commercial games are never bundled and never committed.** The visitor loads their own, and nothing is uploaded. (Rule 4.)
- **No figure describing the project as it stands is typed by hand.** The home page count, every pass count, the frame hash and every speed come from the registry, the test results and a command whose output is kept. (Rule 5.)
- **Document as you go.** Each task ends by adding to that day's journal entry in `docs/journal/`: what was built, what the tests showed, what surprised, and each decision with what it was chosen over. A difference from a reference also goes in `docs/known-differences.md`. (Rule 6.)
- **Both regions are built and both are tested.** A test that touches timing, the APU tables or the frame size runs for `Region.Ntsc` and `Region.Pal`, as a `Theory`. Dendy is refused with a plain message. (Spec "Decisions".)
- **The page says what is not modelled:** Dendy, the Famicom Disk System and expansion audio, the Zapper and other peripherals, the unlicensed mappers, and the analogue quirks of the picture. (Spec "What is left out".)
- **Names:** namespace `Dbhq.Machines.Nes`; projects `src/Dbhq.Machines.Nes/`, `src/Dbhq.Machines.Nes.Wasm/`, `tests/Dbhq.Machines.Nes.Tests/`; all in `6502.slnx`.
- **Warnings are errors** (`Directory.Build.props`: `net10.0`, nullable, implicit usings, `TreatWarningsAsErrors`).
- **British English, and no em or en dashes** in code, comments, docs and the site. CI checks the dashes.
- **The site's copy rules hold:** headings carry no trailing full stop, and `site/tests/` has its own content checks, which must pass.
- **Git:** all work is on branch `implement-nes`, one commit per task with a conventional-commit message, pushed after each. A draft pull request is opened after task 1 so `Validate` runs on every push, and marked ready after task 15. It is merged only when `Validate` is green and Dan says so, because merging deploys and changes the live count.
- **Stay on the branch.** Never switch, create or move to another branch or worktree except as this plan says. Never edit `/home/devops/dbhq-uk/6502` or the worktree of `feat/nes-models`.

## Review Focus

The inputs and conditions the spec implies and no task's main tests would exercise. Each line has its test in the task that owns the code.

1. **A visitor's ROM is bad:** an empty file, a header with the wrong magic, a file shorter than its header says, a trainer, an unsupported mapper, a file of many megabytes. Expected: a plain one-line message naming the cause, and no crash, hang or huge allocation. (Task 2, and task 14 for the size limit.)
2. **The header names Dendy, or a region that disagrees with the visitor's choice.** Expected: Dendy is refused with a message. A PAL ROM run as NTSC runs, at the wrong speed, and the page says which region it chose and why. (Tasks 2 and 14.)
3. **The tab is hidden or the page stalls, and the audio buffer is not drained.** Expected: the sample buffer drops the oldest samples at its capacity and does not grow without bound. (Task 9.)
4. **Both d-pad directions, or Select and Start with everything else, held at once.** A keyboard can do what a pad cannot. Expected: the machine takes any 8-bit mask and reports it as written, and the page does not filter it. (Task 7.)
5. **A cartridge with battery-backed PRG RAM is reset, or the page reloaded.** Expected: a reset keeps PRG RAM and a power cycle clears it. The page says plainly that a reload loses it, because saving is not built. (Tasks 10 and 11.)

## Facts every task relies on

Read these once. Each task names the sheet sections it needs. **The numbers below were first written from memory of the nesdev wiki. Task 1 checked every one against its wiki page on 5 October 2026 and corrected this list where it was wrong; the sheets in `docs/nes/facts/` give the page for each, and the journal entry "Planning the NES" lists what changed. Anything still marked [guessing - verify] is open.**

- **Clocks.** NTSC: master 21.477272 MHz, CPU master / 12 = 1.789773 MHz, PPU master / 4, so 3 PPU dots a CPU cycle. PAL: master 26.601712 MHz, CPU master / 16 = 1.662607 MHz, PPU master / 5, so 3.2 dots a cycle (16 dots in 5 cycles). The wiki gives the ratio and not which cycle carries the fourth dot; from the dividers it is one cycle in every five (3, 3, 3, 3, 4), and the phase a console powers up in is [guessing - verify]. (`timing.md` 1 and 3.)
- **Frame.** 341 dots a line. NTSC 262 lines, pre-render line 261, with one dot dropped from the pre-render line on odd frames when rendering is on. PAL 312 lines, pre-render line 311, no dropped dot. The VBlank flag is set at line 241 dot 1 in both and cleared at dot 1 of the pre-render line (on PAL this is implied by the 70 lines and not confirmed on the wiki: [guessing - verify]). VBlank is 20 lines on NTSC and 70 on PAL. (`timing.md` 2.)
- **PPU reset position.** `nestest.log`'s first line reads `PPU:  0, 21 CYC:7`: after the 7 reset cycles the PPU is at line 0 dot 21, so power-on is line 0 dot 0 and nothing ticks before the first reset cycle. (Seen in the pinned log, which is Nintendulator's; a real console powers up in one of several alignments. `timing.md` 4.)
- **APU frame counter** (CPU cycles). NTSC 4-step: 7457, 14913, 22371, 29828 to 29830. NTSC 5-step: 7457, 14913, 22371, 37281. PAL 4-step: 8313, 16627, 24939, 33252 to 33254 (corrected: memory had 33253 to 33255). PAL 5-step: 8313, 16627, 24939, 41565. The wiki now gives these in APU cycles; the CPU cycles are put = 2n + 1, get = 2n (`apu.md` 10).
- **Noise periods.** NTSC: 4, 8, 16, 32, 64, 96, 128, 160, 202, 254, 380, 508, 762, 1016, 2034, 4068. PAL: 4, 8, 14, 30, 60, 88, 118, 148, 188, 236, 354, 472, 708, 944, 1890, 3778.
- **DMC rates.** NTSC: 428, 380, 340, 320, 286, 254, 226, 214, 190, 160, 142, 128, 106, 84, 72, 54. PAL: 398, 354, 316, 298, 276, 236, 210, 198, 176, 148, 132, 118, 98, 78, 66, 50.
- **OAM DMA** stalls the CPU 513 cycles, or 514 when the halt lands on a get cycle and an alignment cycle is needed. Get and put are the two halves of an APU cycle, and which CPU cycle parity is a get is random at power-on, so "514 on an odd cycle" is one choice of the two (corrected: memory said odd cycle, as if fixed). DMC DMA normally steals 3 cycles for the first fetch after `$4015` and 4 for later ones, 2 inside an OAM DMA, and 1 or 3 at its end, and a CPU write delays its halt (corrected: memory said "up to 4"). (`bus.md` 5 and 6.)
- **The proof ROMs** report through RAM: `$6001` to `$6003` hold a signature when the protocol is in use (the readme writes it `$DE $B0 $G1`, and `$G1` is not hexadecimal, and task 4 read `DE B0 61` from the ROMs and saw all ten singles write it), `$6000` is `$80` while running and the result code after (0 is a pass, `$81` asks for a reset), and the text is a zero-terminated string from `$6004`. Results `$00` to `$7F` are final; 1 is a failure and 2 and up a numbered reason. (`cartridge.md` 5.)
- **The fork** `dbhq-uk/nes-test-roms` is at commit `95d8f621ae55cee0d09b91519a8989ae0e64753b`, the same as `Pins.NestestCommit`. It holds `instr_test-v5`, `instr_timing`, `cpu_interrupts_v2`, `ppu_vbl_nmi`, `sprite_hit_tests_2005.10.05`, `sprite_overflow_tests`, `apu_test`, `apu_mixer`, `pal_apu_tests`, `dmc_dma_during_read4`, `mmc3_test_2` and `other/`, which holds `nestest` and a number of homebrew ROMs. It does not hold `ppu_sprite_hit` or `ppu_sprite_overflow`, which the spec names. `mmc3_test_2` has only `rom_singles/`. **`ppu_vbl_nmi/ppu_vbl_nmi.nes` is MMC1 (mapper 1, 256 KB PRG, CHR RAM), so it cannot run before task 10; its ten `rom_singles/` are NROM (32 KB PRG, 8 KB CHR) and can run in task 4.** (`cartridge.md` 4 and 5.)

### Task 3: The bus, the machine, and nestest through the real bus

**Files:**
- Create: `src/Dbhq.Machines.Nes/NesBus.cs`, `Nes.cs`, `NesOptions.cs`, plus private stubs for the PPU and APU inside `NesBus.cs` that later tasks replace (`Ppu` and `Apu` classes are created in tasks 4 and 8)
- Test: `tests/Dbhq.Machines.Nes.Tests/NesBusTests.cs`, `NestestOnTheBusTests.cs`

**Interfaces:**
- Consumes: `Cartridge`, `IMapper`, `Region` (task 2), `IBus`, `Cpu` (core).
- Produces:
  ```csharp
  public sealed class NesBus : IBus
  {
      public NesBus(Cartridge cartridge, Region region, NesOptions? options = null);
      public Cpu? Cpu { get; set; }                 // the bus drives Cpu.Nmi and Cpu.Irq each cycle
      public Region Region { get; }
      public long Cycles { get; }                   // CPU cycles since power on, DMA stalls included
      public long PpuDots { get; }                  // dots since power on (task 3's stub counts; task 4's PPU replaces it)
      public byte Read(ushort address);  public void Write(ushort address, byte value);
      public byte Peek(ushort address);             // no cycle, no side effect
      public void PokeRam(ushort address, byte value);   // for tests
  }
  public sealed class NesOptions { public int SampleRate { get; init; } = 48_000; }
  public sealed class Nes
  {
      public Nes(Cartridge cartridge, Region? region = null, NesOptions? options = null);   // region defaults to the header's, else NTSC
      public NesBus Bus { get; }  public Cpu Cpu { get; }  public Region Region { get; }
      public void PowerOn();                        // chips cleared, RAM as the sheet says, then Cpu.Reset()
      public void Reset();                          // the console's reset button: the CPU resets, PRG RAM is kept
      public int Step();  public void Run(long cpuCycles);
  }
  ```

**Built from:** `bus.md` (memory map, mirrors, open bus), `timing.md` (the dot ratio and its accumulator).

**What it must do.**
- `$0000-$1FFF` is 2 KB RAM mirrored four times. `$2000-$3FFF` is the PPU's 8 registers mirrored (stubbed now: reads return the open-bus latch, writes are kept for task 4). `$4000-$4017` the APU and I/O (stubbed). `$4020-$FFFF` the mapper. Open bus: a read of an unmapped address returns the last value on the bus (`bus.md`), and the latch updates on every read and write.
- **One place runs a cycle:** `Cycle(access)`. It advances the dot accumulator, ticks the PPU the region's number of dots, ticks the APU, drives `Cpu.Nmi` and `Cpu.Irq` from the chips, and does the access. The order within the cycle (dots before, after or around the access) is task 4's decision, so `Cycle` keeps it in one method with the first version "all dots, then the access". `Cycles++` happens only inside `Cycle`, so no cycle is counted without an access and no access happens outside one.
- The dot accumulator is integers: `accumulator += DotsNumerator; dots = accumulator / DotsDenominator; accumulator %= DotsDenominator`. NTSC gives 3 every cycle, PAL gives 3,3,3,3,4 in a pattern that sums to 16 in 5 (the order inside the five is task 4's, recorded in `timing.md`).

- [ ] **Step 1: Write the failing tests.**
  - `NesBusTests`, for both regions as a `Theory`: RAM reads back at `$0000` and `$07FF`, and mirrors at `$0800`, `$1000` and `$1800`. A write to `$8000` on NROM is ignored. `Peek(0xFFFC)` and `Peek(0xFFFD)` match the cartridge's last four bytes read from the test's own array. A read of `$5000` (unmapped) returns the byte the last access left, and a write of `$AB` to `$5000` then a read of `$5001` gives `$AB`. **Files:**

**Interfaces:**
- Produces, in `NesHost` (`[JSExport]`, as `BbcHost`):
  ```csharp
  static string RegionOf(byte[] rom)                       // "NTSC", "PAL" or "" when the header does not say; throws with the cartridge's plain message when the ROM is bad
  static string Load(byte[] rom, string region, int sampleRate)   // region "NTSC", "PAL" or "" (use the header, else NTSC); returns one sentence saying which was chosen and why; powers on
  static double Run(int cycles)                            // returns the cycles since power on
  static void SetButtons(int pad, int mask)
  static void Reset();  static void PowerCycle();
  static double Frames();
  static void Picture();  static void Sound();             // hand a view of the frame and of the samples to the page's imported picture and sound functions, as the BBC's do
  ```
  The page's JavaScript registers `picture` and `sound` in the module `nes` before it calls `Load`.

**The panel.**
- **Screen:** a `<canvas>` of 256 by 240 filled from the frame view once per `Frames` change, shown in the region's pixel shape: 8:7 on NTSC, which makes 4:3, and about 1.386:1 on PAL (`ppu.md` 10, from the wiki's Overscan page, which suggests a multiple of 355 by 240), with a line saying it models the picture and is not a CRT. The shape follows the region control.
- **Region:** a control for NTSC or PAL. It starts from `RegionOf` where the header says, and the line under it says which was chosen and why ("the file says PAL", "the file does not say, so NTSC"). Changing it restarts the machine and says so. A bad file shows the cartridge's message and the machine stays as it was.
- **Input:** keyboard by `event.code` for pad 1 (arrow keys, `KeyZ` for B, `KeyX` for A, `Enter` for Start, `ShiftRight` for Select), and the Gamepad API for pads 1 and 2 by index, standard mapping. Focus rules as the other panels: Tab and Escape do not trap the page. An on-screen pad for touch.
- **Sound:** off until the visitor clicks "Turn sound on" (browsers block autoplay); `nes-audio.js` is an `AudioWorklet` that drains the sample buffer; a hidden tab makes the buffer drop samples and not grow (Review Focus 3), and the panel says sound is off when it is.
- **ROM picker:** a file input and a drop target. The file is read in the browser and never uploaded. A file over the cartridge's size limit is refused by the page before it is read in full, using the same limit read from the build, not typed.
- **Reset and power:** a Reset button (keeps PRG RAM) and a Power button (clears it). The page says plainly that **saving is not built, so a page reload loses battery RAM** (Review Focus 5).
- **Start button:** the WebAssembly downloads on click, not on page load, and the button says how large the download is, read from the built file sizes.

Run: fails.
- [ ] **Step 2: Implement `NesHost`,** as `BbcHost`'s shape, with the same view-not-copy handover for the picture and the sound, and write `nes.js`, `nes-audio.js` and `NesPanel.astro`.
