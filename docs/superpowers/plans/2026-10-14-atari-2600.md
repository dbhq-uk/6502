# The Atari 2600: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Atari 2600, NTSC and PAL, on the core: it passes its chip tests and every trusted test of the pinned `missingno-vcs-tests` suite in both regions, every recorded test gives its recorded outcome, the bundled homebrew boots to its recorded frame, and it runs in the browser at 6502.dbhq.uk with picture, sound, two joysticks and the console switches, as the design in [`../specs/2026-10-14-atari-2600-design.md`](../specs/2026-10-14-atari-2600-design.md) says.

**Architecture:** A new library `Dbhq.Machines.Atari2600` on the `Nmos6502` core. An `Atari2600Bus` derives from the core's `Bus`. Every `Read` or `Write` is one CPU cycle: the bus keeps the low 13 address lines, decodes the TIA, the RIOT and the cartridge, advances the TIA by three colour clocks and the RIOT by one cycle, and shows the access to the cartridge's board. The WSYNC halt is the bus running repeated read cycles inside one `Read` call, as the NES's DMA halt is. A `Region` value holds every number that differs between NTSC and PAL. Each chip is its own class, tested alone, written from the fact sheets in `docs/atari-2600/facts/` and never from another emulator's code. The shared browser host runs the page, and the parts of the NES's panel a second console needs move into shared modules.

**Tech Stack:** C# on .NET 10, xUnit 2.9.3 (the version the other test projects use), .NET WebAssembly compiled ahead of time for the browser, plain JavaScript modules and an `AudioWorklet` for the page, Astro for the site, headless Chrome for the real-browser check.

**This plan has NOT been pre-run**, in the form the BBC Micro's, the Electron's and the NES's plans took and for the same reason: the TIA is thousands of lines, so its code is not written here. Each task states its interfaces, the facts it is built from and the exact assertions; the implementer writes the tests first and the code to pass them, and a reviewer gates each task. The C# blocks below are interfaces, which cannot compile before their code exists. The shell commands that only read the two forks were run on 14 October 2026 while this plan was written, and their results are quoted with that date. The spec asks for "every code block compiled and run before it goes in"; that is not met by this form, and Dan is told (see "Open points" below). What is proven early is the risky part: task 4 runs the suite's `cpu/`, `riot/` and `harness/sanity` self-tests through the real bus, task 5 settles the order of the colour clocks inside a cycle against the suite's timing tests, and task 8 measures the speed in a browser on a CI runner before the sound and the input exist.

**Spec:** [`docs/superpowers/specs/2026-10-14-atari-2600-design.md`](../specs/2026-10-14-atari-2600-design.md). The speed pass (issue [#130](https://github.com/dbhq-uk/6502/issues/130)) and the 3D models (issue [#129](https://github.com/dbhq-uk/6502/issues/129)) are **not** in this plan. Each is a later pull request with its own design and plan.

## Global Constraints

- **Every bus access is one cycle.** `Atari2600Bus.Read` and `Write` are one CPU cycle each and advance the TIA and the RIOT inside the call, in one method, `Cycle`, which is the only place a cycle is counted. A WSYNC halt is the bus running more read cycles inside one `Read` call before it returns, each through `Cycle`. The CPU's dummy reads and the second write of a read-modify-write reach the bus like any other access, which the bank switching depends on. (`AGENTS.md` rule 1; spec "The bus, the halt and the order inside a cycle".)
- **The core knows no machine.** Nothing under `src/Dbhq.Cpu6502/` changes or names the 2600. The 6507's 13-bit address is the bus's: the core puts out 16 bits and the bus drops the top three. The WSYNC halt is in the bus, not a RDY line in the core. The bus never raises IRQ or NMI, because the 6507 has neither pin. (Rule 2; spec "The 6507 on the core".)
- **No code from another emulator.** Stella and Gopher2600 are GPL, and missingno is left out because the suite was developed beside it. The chips are written from the fact sheets. The suite's test headers are read as a statement of the behaviour to match. missingno's test harness (`crates/systems/vcs/tests/accuracy/common/mod.rs` in the fork) is read only for the protocol numbers it states, which are quoted with their place in the fact sheet; none of its code is copied. (Spec "Where the code comes from".)
- **Inputs come only from the two `dbhq-uk` forks, at the pinned commits, and every file is hash-checked.** `dbhq-uk/missingno-vcs-tests` at `891c079976a2f68033ca4af2fe2fd85aaf1906c9` (the sources, their headers and the reference pictures) and `dbhq-uk/missingno` at `a4159f47ce7ef6f9c3d5402a8c58b18940045adc` (only `crates/systems/vcs/tests/accuracy/roms/`, the prebuilt `.a26` files). Each file's hash is in a committed manifest whose own SHA-256 is in `Pins.cs` with the two commits. `site/tests/mirrors.test.mjs` already fails on a fetch from any other host. (Rule 3; spec "Forks and issues".)
- **The bundled game is 2048 2600, the author's own build, committed in `machines/atari-2600/cartridges/2048/`** (`2048.bin`, the MIT licence text as its author published it, a README with the provenance, the pinned commit `35de3c1` and the SHA-256, and an SPDX manifest, listed in `machines/atari-2600/cartridges/manifest.json`), under `AGENTS.md`'s rule for bundled programs, which covers cartridges the same way it covers discs; its MIT notice in `NOTICE.md`, its rights in the registry, and its SHA-256 checked each time it is read. The NES's Lan Master in `roms/nes/` predates that rule and stays where it is; moving it is a separate chore. Commercial games are never bundled and never committed; the visitor loads their own, and nothing is uploaded. (Rules 3 and 4; spec "ROMs and rights". Dan decided the folder on 14 October 2026; open point 1, below.)
- **No figure describing the project as it stands is typed by hand.** Pass counts, recorded outcomes, frame hashes and speeds come from test output, a recorder or a workflow run, each with its command. (Rule 5.)
- **Document as you go.** Each task ends by adding to that working day's entry in `docs/journal/`: what was built, what the tests showed, what surprised, and each decision with what it was chosen over. A journal summary carries no digits (write "the Atari VCS", not the model number), because the home page reads digits in a summary as figures. A difference from a reference goes in `docs/known-differences.md`. (Rule 6.)
- **Both regions are built and both are tested.** A test that touches the clock, the palette, the frame or the picture window runs for `Region.Ntsc` and `Region.Pal` as a `Theory`. SECAM is not modelled.
- **The page says what is not modelled**, each with its issue: SECAM ([#106](https://github.com/dbhq-uk/6502/issues/106)), the boards beyond the first version ([#107](https://github.com/dbhq-uk/6502/issues/107), and one issue per board, [#131](https://github.com/dbhq-uk/6502/issues/131) to [#155](https://github.com/dbhq-uk/6502/issues/155)), the paddles ([#108](https://github.com/dbhq-uk/6502/issues/108)), the keypads ([#124](https://github.com/dbhq-uk/6502/issues/124)), the driving controller ([#125](https://github.com/dbhq-uk/6502/issues/125)), board detection from the image ([#126](https://github.com/dbhq-uk/6502/issues/126)), other peripherals ([#127](https://github.com/dbhq-uk/6502/issues/127)), and the analogue picture with PAL colour loss ([#128](https://github.com/dbhq-uk/6502/issues/128)).

## The suite's results, and what each one gates

The spec's trust split, as CI enforces it. Task 1 writes `docs/atari-2600/facts/suite.md`, which lists every test with its kind (self-test or screenshot), its status below, the parts of the machine it needs, and so the task in which it should first pass.

|---|---|---|
| Self-tests in `cpu/`, `riot/`, `collision/`, `tia-timing/`, `tia-render/` and `harness/sanity`, both regions | **Trusted** | A `Theory` row each in `SuiteSelfTests`; each must give `$A5` at `$80` within the limit. On a fail the message gives `$81` to `$83` |
| `cartridge/mirror-2k`, `bank-f8`, `bank-f6`, `bank-f4`, both regions | **Trusted** | As above |

| Screenshot tests (`tia-timing/`, `tia-render/`, `harness/calibration`), both regions | **Recorded** | Run in CI; the count of mismatched pixels by the partition rule must equal the recorded count. A non-zero count is triaged as a likely bug first |

**Recorded** outcomes are written only by the recorder (`ATARI_RECORD=1 dotnet test tests/Dbhq.Machines.Atari2600.Tests --filter Record`), never by hand. A changed outcome fails CI; the change goes in the journal before the file is recorded again. A trusted test that fails is fixed, or moves to recorded with a `docs/known-differences.md` entry giving its cause and Dan's agreement. Nothing is skipped silently.

## Fixed before running

Every quantitative check in this plan, with its number, fixed now. A result that crosses one stays recorded as crossed; the number is not moved to fit a result. Where a number comes from the suite's own harness it is the protocol the suite was written for, read from the fork on 14 October 2026.

1. **A self-test's limit:** a verdict (`$A5` or `$5A` at `$80`) within 5,000,000 instructions from power on, counted as calls to `Cpu.Step` (the harness's `MAX_INSTRUCTIONS`). No verdict in that time is a failure reported as "no verdict" with the byte at `$80`.
2. **The frame's line limit:** 400 lines. A frame ends at the end of VSYNC or when it reaches 400 lines without one (the harness's `FRAME_LINE_BUDGET`, above PAL's 312 with room). This is also the machine's own limit, the spec's "up to a limit".
3. **The screenshot frame:** the eighth frame after power on (the harness runs eight frames and keeps the last).
4. **The screenshot alignment:** row 0 of our frame is the first line after VSYNC ends, and the comparison covers the rows both pictures have, 160 pixels wide. The suite's README says a reference covers "every scanline after the three VSYNC lines", and its harness's comment says references "carry the VSYNC-period lines" that its frame drops; the two disagree. So the alignment is checked once on `harness/calibration`, a test whose picture is unambiguous, in both regions before any other screenshot test is compared (Dan, 14 October 2026: fix it once, on calibration): if calibration matches best at a constant offset of k rows, k is recorded in the fact sheet and the journal and used for every test, never chosen per test. The suite's real-console PAL captures (`*_pal_capture.png`) are **not compared in the first version**; issue [#162](https://github.com/dbhq-uk/6502/issues/162) tracks them as recorded-only evidence.
5. **The partition rule:** for each colour in the reference, the TIA colour number found most often under it in our frame is its match (a tie goes to the lower number). If two reference colours match one number, the less frequent keeps no match. A pixel is mismatched when our colour number is not its reference colour's match. The outcome is the count of mismatched pixels; a pass is zero.
6. **The Superchip by its filler, on the suite's own files:** `ram-superchip` is detected as F8 with the Superchip, and `bank-f8`, `bank-hotspot-window` and `power-on-bank` as F8, `bank-f6` as F6 and `bank-f4` as F4, all without it. (Checked on 14 October 2026 by reading the first 256 bytes of each 4K bank of the `_ntsc` builds from the fork: only `ram-superchip` has one repeated byte there in every bank.)
7. **The boot check:** NTSC with the colour switch at colour, PAL with it at black and white (the game makes PAL frames only then), 120 frames on NTSC and 100 on PAL, a frame being ended as in item 2. If the picture at that frame is blank, that is a finding: the count is not moved to find a picture, and the spec's fallback (Core Escape, then a test ROM) applies.
8. **The order inside a cycle:** of the four splits (0, 1, 2 or 3 of the cycle's colour clocks before the access, the rest after), the one that passes the most trusted `tia-timing/` self-tests is kept. A tie goes to the split the fact sheet's sources state; if they state none, to the fewest clocks before the access. (`tia.md` section 4, 14 October 2026: the sources state the end of the cycle, all three clocks before the access; the split and the WSYNC release point are seen only together; and the delays each register adds after the write lands are the TIA's own, in its paths, not a split.)
9. **The speed milestone's rule (the NES plan's):** the AOT median, as a multiple of real time from `Region.CpuHz`, on the bench program in item 10. At least 25 times: continue. From 10 to 25: continue, and the page's headroom line says so. Under 10: stop and tell Dan before the sound is built.
10. **The speed bench:** `harness/calibration_ntsc.a26` on NTSC and `_pal.a26` on PAL (the capture-rig target, which draws every line), run for 60 frames to settle, then `Run` of one second of machine time timed five times, best and median, AOT and interpreter, on a GitHub runner by a hand-started workflow, with the host recorded first and the load checked before each launch as `bbc-speed-run.yml` does it, and the verdict printed.
11. **The samples:** one second of machine time gives the sample rate's count of samples, plus or minus 1, in both regions.
12. **The resampler:** the box filter is kept if, for `AUDC` 4 at `AUDF` 0, 15 and 31 and volume 15, in both regions, the strongest component that is not a harmonic of the tone is at least 40 dB below the fundamental at 48,000 samples a second; otherwise the band-limited step is used.
13. **The PAL suggestion on the page:** shown when the median line count of the last 30 frames is nearer `Region.Pal`'s nominal lines than `Region.Ntsc`'s, and the region is NTSC.
14. **The browser check's frame:** the canvas's RGBA bytes after the bundled game's recorded frame count hash to the `rgba` value in `expected-frames.json`, exactly.

## Review Focus

The inputs and conditions the spec implies and no task's main tests would exercise. Each has its test in the task that owns the code.

1. **A read-modify-write, or a dummy read, on a hotspot or a strobe.** `INC $1FF8` touches the hotspot three or four times; a page-crossing `LDA $10F0,X` reads the Superchip's write port by accident; `DEC WSYNC` writes twice before it halts. Expected: each bus access counts once, as the hardware sees it. (Tasks 2 and 4.)
2. **A file that is not a cartridge this machine models.** Empty, one byte, 3 KB, 64 KB, 10 MB, an 8K E0 game. Expected: a plain sentence naming the size and the boards that are modelled, the machine left as it was, no exception in the console and no large allocation; an 8K E0 game runs as F8 and the page says so. (Tasks 2 and 13.)
3. **A program that never strobes VSYNC, or strobes it every few lines.** Expected: a frame still ends at the line limit, the page draws it as it is, the line count shows it, and nothing hangs or grows. (Tasks 5 and 13.)
4. **Every joystick direction and both fire buttons held at once, and switches held through a reset.** A keyboard can do what a joystick cannot. Expected: the machine takes any combination and reports it as written; the page does not filter it. (Tasks 9 and 13.)
5. **The region switched while a game runs, and a hidden tab.** Expected: the palette and the clock change at once with no restart, the sample buffer drops the oldest samples at its capacity and never grows, and the headroom line follows the new clock. (Tasks 10 and 13.)
