# 14 October 2026: the plan for the Atari 2600

The design merged earlier today, [`2026-10-14-atari-2600-design.md`](../superpowers/specs/2026-10-14-atari-2600-design.md), and this entry records the session that wrote its plan, [`2026-10-14-atari-2600.md`](../superpowers/plans/2026-10-14-atari-2600.md). It is a docs-only change: no code was written and no issue was filed. Merging it starts no code.

## The form

The plan takes the form of the NES's and the Electron's: each task names its files, its interfaces, the facts it is built from and its exact assertions, and the implementer writes the tests first. It keeps the spec's fifteen tasks in the spec's order and sizes, and adds to each what done means, a review focus naming the constraint at risk, and the issues it closes or comments on, read from the live list labelled `atari-2600`. The NES's lazy chips taught that the hooks for a speed pass are cheaper built early, so task 4 builds them, as the spec asks.

## Fixed before running

The BBC Micro's models showed that a check whose number is chosen after the result is not a check, so the plan lists every number up front: the self-test limit, the frame's line limit, which frame a screenshot compares, how the rows line up, the partition rule, the Superchip expectations, the boot frames, the rule for the order inside a cycle, the speed rule and its bench, the samples, the resampler, the PAL suggestion and the browser check's frame. The self-test limit, the line limit and the screenshot frame are the suite's own harness's numbers, read from `crates/systems/vcs/tests/accuracy/common/mod.rs` in the `dbhq-uk/missingno` fork at its pinned commit. Only the numbers were taken; the spec keeps missingno's code out.

## What was checked, and how

All of it on 14 October 2026, from the two forks only.

- **The suite's tree** at `891c079`, through `gh api repos/dbhq-uk/missingno-vcs-tests/git/trees/891c079976a2f68033ca4af2fe2fd85aaf1906c9?recursive=1`: every test's source, and the reference pictures.
- **The binaries' tree** at `a4159f4`, the same way: each test has an NTSC, a PAL and a SECAM binary, and none is missing.
- **The Superchip rule on the suite's own files.** The first 256 bytes of each 4K bank of the `_ntsc` cartridge binaries were read from the fork with a short Python script: only `ram-superchip` holds one repeated byte there in every bank, so the spec's rule picks it out and leaves `bank-f8`, `bank-f6`, `bank-f4`, `bank-hotspot-window` and `power-on-bank` alone. The plan fixes that as an expected result.
- **The README and the harness**, read for how a test reports and how its picture is compared.

## What the design did not know

**The suite disagrees with itself about its pictures.** Its README says a reference covers every line after the three VSYNC lines; its harness says the references carry the VSYNC lines its frame leaves out. The plan settles the alignment once, on the calibration test, before any other picture is compared, and never per test.

**The suite keeps real-console captures** (`*_pal_capture.png`) beside its references. They are stacked stills off the RF output, not pixel-exact, so the plan does not compare them; they could be a later issue.

**Pinning each file in `Pins.cs`** would mean a few hundred lines there. The plan records them in a manifest from the forks' trees, as Harte's data is recorded, and pins the manifest's hash in `Pins.cs`.

## Points for Dan

The plan follows the spec on each and lists them in its "Open points" section: where the bundled game lives (the spec says `roms/`, as the NES's is; `AGENTS.md` rule 3 says a bundled program goes in `machines/<id>/discs/`); a second hand-started speed workflow in CI, which `AGENTS.md` calls a single exception today, and which must reach `main` before it can be started; the spec's wish for every code block to be compiled and run, which this form of plan does not meet; the manifest in place of one pin a file; and the two findings above.
